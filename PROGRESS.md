- [x] **M6 — Automatic floor-plan understanding** (2026-09-26)
  - **Supported input defined:** `docs/SUPPORTED_FLOOR_PLANS.md` covers the format, resolution (walls ≥ ~4 px, about 50+ px/m), drawing style (solid thick axis-aligned walls, arc doors, line windows, dark on light), scale assumptions, limits and what happens with each unsupported case.
  - **CV pipeline** `backend/app/interpretation/opencv/`: preprocess (binarize, polarity, deskew ≤ 10°, reject blank/photo/dark images) → walls (stroke-thickness histogram + morphology, collinear merge, junction snapping, gap bridging) → rooms (enclosed free space snapped to wall centrelines) → openings (door arcs incl. narrower doors next to junctions, window lines, unknown gaps left open) → scale (median door width, plausibility-checked) → assemble (schema-valid FloorPlan, omit < 0.5 confidence, never calibrated). Each stage returns typed intermediate data; per-element confidence and a report travel beside the unchanged FloorPlan.
  - A previous session had built most of the pipeline and the evaluation harness but never reported them, and the pipeline **crashed on every image under the installed OpenCV 5** (`HoughLinesP` output shape changed). That is fixed, and all numbers were re-measured.
  - **API:** `POST /api/floorplans/{id}/interpret` streams real stage progress (NDJSON) and stores the result as a proposal (`interpretation.json`), never overwriting the saved plan. `GET /api/floorplans/{id}/interpretation` returns it.
  - **UI:** "Auto-generate the floor plan" toggle on upload (on by default) with live stages Uploading → Validating → Analyzing → Detecting walls → rooms → doors & windows → Estimating scale → Building floor plan → Ready for review. A result summary (counts, confidence, warnings, or the rejection reason) leads into the **existing M3 editor**, which opens the proposal as unsaved changes and has an *Automatic detection* review panel (flagged elements with amber highlight, omitted counts, scale source, notes), per-element confidence in the properties panel, and "Auto-detect from image" (undoable) for any uploaded plan. The manual editor, schema and 3D engine are unchanged.
  - **Measured accuracy** (`docs/CV_EVALUATION.md`, `python -m evaluation.run`). Synthetic supported style (30 plans): walls 100% recall / 100% precision, rooms 98.6% / 100%, doors 99.3% / 100%, windows 99.1% / 100%, scale error median 4.0% (worst 7.7%). **Real apartment plan (1, hand-traced truth): walls 8/10, rooms 3/4, doors 1/4, windows 4/6, scale 14% off.** A real 3D render is correctly rejected. ## Decisions
- Project placed in the user home folder, not the shell's working directory (`System32`).
- No database, no auth for the MVP.
- `opencv-python-headless` chosen over full OpenCV (server, no GUI needed).
- M5: room labels are DOM overlays (drei `Html`), not 3D text: always crisp and readable, cheap for tens of rooms, no font assets. Revisit for VR (M8), where DOM overlays do not exist.
- M6: automatic detection is an explicit action that produces a *proposal* (`interpretation.json`); the user's saved plan is only changed by an explicit save in the editor. `GET /structure` stays manual so opening the editor never silently runs CV.
- M6: confidence and warnings live in a separate `InterpretationReport`, not in the FloorPlan, so the schema and the 3D engine did not change.
- M6: progress is streamed as NDJSON from a single request (real stage events) instead of a job queue; enough while a plan takes well under a second.
- M6: user-supplied real test images are kept local (`backend/evaluation/real/`, git-ignored, unknown licence); their ground truth is versioned in `evaluation/cases.py`.
- M7: a buyer link is a **snapshot** published on request, not a live view of the saved plan, so work in progress never reaches buyers; the link stays stable across republishing.
- M7: the public share document holds only what a buyer sees (no floor-plan/project ids, no source image), so the link grants nothing editable even without accounts.
- M7: still no database and no auth: files are enough for one developer on one machine; auth is the first thing to add before real multi-user use.
- M5: OrbitControls damping stays off: with render-on-demand, scripted camera moves and damping inertia would fight; moves are explicit short animations instead.
- M8: plain WebXR + three.js `WebXRManager` instead of `@react-three/xr`: R3F already handles the XR frame loop, the needs are small (one session, controllers via the gamepad API), and it avoids a dependency that loads controller models from a CDN by default.
- M8: VR collision is computed from the generated wall/window meshes, not from the FloorPlan, so it always matches what the visitor sees (trimmed walls, door holes) and needed no engine change.
- M8: the browser test emulates the headset with IWER injected by the test script; the app has no emulation code, so "Enter VR" never appears on a device without a real headset.
